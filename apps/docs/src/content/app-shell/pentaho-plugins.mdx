# Pentaho plugins

A Pentaho plugin's UI is an **App Shell** app that runs inside a Pentaho server's App Shell. `@pentaho/uikit-cli` creates one, runs it locally on sample data and packages it for the server.

> [!NOTE]
>
> Pentaho plugins are in preview, and their server-side files are not yet verified on a Pentaho server: see [Known limits](#known-limits).

<Steps>

### Create a plugin

```sh
npx @pentaho/uikit-cli@latest create job-health -t plugin --title "Job health"
cd job-health
npm install
```

The name is the plugin's id: lowercase words joined by hyphens, and its folder on the server. The CLI needs Node 22.22, 24.15 or 26 and later.

### Run it on sample data

```sh
npm run dev
```

The plugin opens in a local App Shell, with its menu entry and views, and its server calls answered from `samples.json`.

### Check and test it

```sh
npm run check   # format, types and lint, with the UI Kit design rules
npm test        # unit tests
npm run shots   # with npm run dev running: screenshots of the views listed in review/shots.json, for review
```

### Package it

```sh
npm run package
```

`package` (`uikit-cli package`) builds the plugin, checks there is a bundle for every view in `plugin.json`, and writes `job-health.zip`. Pass `--built` to package an existing build.

### Install it on a server

Unzip `job-health.zip` into the server's `pentaho-solutions/system` folder and restart the server. The zip holds one `job-health/` folder:

| File                            | What it is                                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `plugin.xml`                    | The plugin's name and title, and its `webclient/` folder served at `/<id>/webclient`.                      |
| `pentaho-app-shell.config.json` | The menu entry, the provider and the views, which the server's App Shell merges with every other plugin's. |
| `webclient/`                    | The built bundles: one per view, and the provider.                                                         |

</Steps>

## The project

| File                         | What it holds                                                                                                                                                                                                     |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `plugin.json`                | The plugin's id, title, description, menu entry (`label`, `icon`, optional `ordinal` and `parent`, e.g. `settings`) and views (`id`, `title`, `route`). The local App Shell, the build and `package` all read it. |
| `src/pages/<view id>.tsx`    | One page per view, inside the shared `src/components/ViewLayout.tsx`.                                                                                                                                             |
| `src/providers/Provider.tsx` | Wraps every view; add shared context here.                                                                                                                                                                        |
| `src/lib/api.ts`             | The server's APIs, through `serverUrl("api/...")`, so no view hard-codes the server's path.                                                                                                                       |
| `samples.json`               | A response for each server call, used by `npm run dev`.                                                                                                                                                           |

To add a view, add it to `plugin.json` and add its page.

### Samples

`samples.json` maps each server call, `"METHOD /path"`, to its response; a `{param}` segment matches any value:

```json
{
  "$written": "2026-11-19",
  "GET /api/scheduler/getJobs": { "job": [] },
  "GET /api/repo/files/{path}/properties": null,
  "POST /api/scheduler/job": { "$status": 503 }
}
```

- `null` answers with no body, and `{"$status": 503, "body": …}` with that status, to show an error state.
- A call with no sample answers 404 with its name, so a missing sample is never mistaken for an empty list.
- `$written` is the day the samples were written: every date in them moves by the days since, so "3 days ago" stays 3 days ago.
- A state with other data has its own file of only what changes: open the page with `?samples=empty`, or run `SAMPLES=empty npm run dev`, to read `samples.empty.json` over `samples.json`.

## With a coding agent

Set up your agent as for any **UI Kit** app (see [Working with AI](/docs/working-with-ai)):

```sh
npx --no-install uikit-tools init
```

The plugin's `AGENTS.md` lists its commands and structure. For Claude Code, `init` also adds two skills: `pentaho-plugin`, which builds pages from a request or an approved Figma design on sample data and checks them, and `pentaho-plugin-package`, which packages the plugin and reports what the zip holds. Other agents read the same skills from `node_modules/@pentaho/uikit-tools/skills`.

## Known limits

- **Unverified on a server.** `plugin.xml`, `pentaho-app-shell.config.json` and the `webclient/` layout follow the platform's own plugins and the App Shell docs; they have not been tested on a Pentaho server yet.
- **Same versions as the server.** The server's App Shell loads the plugin's bundles, so it needs the App Shell and **UI Kit** versions the plugin was built with.
- **Bundle size.** Each plugin bundles **UI Kit** core: about 330–500 kB per view.
- **Samples ignore query strings.** `GET /api/jobs?page=2` answers from `GET /api/jobs`; use a state file for other data.
- **Real data is the plugin's job.** The template gives the server's base path, its CSRF token and sample responses; calling the right Pentaho APIs, and handling their errors and permissions, is up to the plugin.
